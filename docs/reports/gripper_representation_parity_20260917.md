# 수집↔추론 그리퍼 표현 대조 (2026-09-17)

질문: "수집과 추론이 지금 그리퍼에 대한 모든 표현과 영점이 동일해진 거 맞아?"

**아니다. 그리고 2026-09-16 의 "단위 수정"이 맞춰져 있던 것을 깨뜨렸다.**

## 1. 코드로 확인한 체인

수집:
```
pika_win/recorder.py:451-457   ga = sense.get_encoder_data()["angle"]      # AS5047 엔코더
                               gd = sense.get_gripper_distance()           # mm (4절 링크)
                               arm["gripper"] = [ga, gd]
pika_win/timesync.py:80-82     gripper_synced = 선형보간(gripper)          # 열 순서 보존
openpi convert_pika_umi_storage_video.py:716
                               left_grip = gripper_synced[:, 0]            # <- ga, 즉 "각도"
                        :329   state = ... left_grip / 100.0
```

배포:
```
policy_runner/gripper.py:224   sdk_jaw_mm(motor_rad)                       # mm (같은 4절 링크식)
policy_runner/openpi_remote.py:1225,2133   grip / 100.0                    # state
                              :2693-2694   chunk[:, GRIP] *= 100.0         # action
```

**학습 데이터의 그리퍼 열은 `[ga, gd]` 중 0번, 즉 거리(mm)가 아니라 엔코더 각도다.**
`gd` 는 저장만 되고 학습에 쓰이지 않는다. 이 코퍼스를 읽는 컨버터는 하나뿐이고(위 파일), 두 팔 다
`[:, 0]` 을 읽는다.

→ **이전 진단(2026-09-16, "수집=mm(sense 거리), 배포=모터 각도 비율")은 열을 잘못 읽은 것이다.
   실제는 정반대다: 수집이 각도, 배포가 mm.** 그래서 09-16 수정이 성능을 떨어뜨렸다
   (carry 16%/28% → 1%/10%).

## 2. 얼마나 어긋나 있나

`angle` 은 도(degree)로 보인다 — SDK 가 AS5047 에서 `{'angle', 'rad'}` 를 쌍으로 싣고,
학습 norm stats 의 q99 = 73.97 을 180/π 로 나누면 1.291 rad 으로 조의 기계 범위
[0, 1.674] 안 77% 지점에 떨어진다(사람이 낼 만한 최대 개구). **다만 실제 에피소드 파일로
`angle == rad × 180/π` 를 직접 확인하지는 못했다** — /data/pika 가 이 호스트에 미마운트.
(각도가 도가 아니더라도 "수집=각도, 배포=mm" 이라는 불일치 자체는 코드로 확정이다.)

도라고 두면, 정책이 값 v 를 냈을 때:

| v | 학습 의도 rad | 의도 조 개구 | 지금 배포가 여는 값 | 오차 |
|---:|---:|---:|---:|---:|
| 8 | 0.140 | 5.7 mm | 8.0 mm | **+2.3** |
| 12 | 0.209 | 8.9 | 12.0 | +3.2 |
| 20 | 0.349 | 15.6 | 20.0 | +4.4 |
| 28 | 0.489 | 23.1 | 28.0 | **+4.9** |
| 32 | 0.559 | 27.1 | 32.0 | +4.9 |
| 50 | 0.873 | 46.8 | 50.0 | +3.2 |
| 74 | 1.292 | 74.9 | 74.0 | −0.9 |

최대 +4.95 mm, 의도 조 개구 25.3 mm 에서. 09-16 하드웨어 실측 노트의
"+4.85 mm, 물리 23 mm 조에서 최대"와 같은 곡선이다.

방향이 두 군데서 겹쳐 나빠진다:

- **액션**: 모델이 "28"(=23.1 mm 의도)을 내면 러너는 28 mm 를 연다 → **항상 더 벌어진다**
- **proprio**: 물리 23 mm 를 모델에게 0.23 으로 준다. 모델의 단위에서 그 상태는 0.28 이다
  → **모델은 조가 실제보다 더 닫혀 있다고 믿는다**

09-16 이전의 옛 percent 는 `rad/1.75×100 = rad×57.143` 이었고 도는 `rad×57.296` 이라 둘이
0.27% 차이다. **즉 옛 배포는 우연히 학습 표현과 거의 정확히 일치하고 있었다.**

## 3. 영점

양쪽 다 rad = 0 에서 0 을 정의한다(도는 자명하게, `sdk_jaw_mm` 은 `half(0)` 을 빼서). 문제는
두 장치의 rad 0 이 같은 물리 상태냐다.

- 배포: `_home_one` 이 닫힘 기계 스톱에서 모터를 재영점 → rad 0 = 물리적으로 닫힘 (코드로 강제)
- 수집: Sense 의 `encoder_data['rad']` 는 장치 펌웨어 값 그대로. SDK 에 `set_zero()` 는
  **gripper.py 에만** 있고 sense.py 에는 없다. `config/gripper_calib.json` 은 에피소드 토글용
  더블-핀치 제스처(`pika_win/gesture.py`)에만 쓰이고 기록값에는 관여하지 않는다.

→ **영점 일치는 여전히 미검증이다.** 공통 물리 기준(같은 게이지 물체를 Sense 와 로봇 그리퍼에
동일하게 물리고 양쪽 `get_gripper_distance()` 를 읽기)이 필요하다. 다만 §2 의 스케일 오차가
지배적이므로 순서는 스케일 먼저다.

## 4. 권고

체크포인트는 이미 각도로 학습돼 있다. 데이터를 다시 변환하면 3종 학습을 전부 다시 돌려야 하므로,
**배포를 학습 표현으로 맞추는 쪽이 유일하게 합리적이다.**

`GRIPPER_UNITS` 에 `encoder_deg` 를 추가해 proprio 와 target 양쪽을 `rad × 180/π` 로 쓴다.
`motor_fraction` 에 `max_rad = 100·π/180 = 1.745329` 를 주면 수치적으로 같지만, `max_rad` 는
명령 클램프(실측 기계 스톱 1.6741 rad)도 겸하므로 **표현 스케일과 클램프를 분리**해야 한다.
옛 동작으로 되돌리는 것(max_rad 1.75)은 0.27% 어긋난 근사일 뿐이다.

## 5. 실기 결과로 검증 — **이건 진짜 문제가 아니다** (2026-09-17 추가)

§4 의 권고를 실행하기 전에 실기 런으로 검정했다. 설정을 고정하고(devjit_40k / execute 4 /
lookahead 없음 / RTC 1 / proprio=actual) 09-16 단위 변경 전후를 배달율로 비교:

| | 시도 | 배달 | 배달율 | 95% CI |
|---|---:|---:|---:|---|
| 변경 전 (~09-15) | 755 | 219 | **29.0%** | [25.9, 32.3] |
| 변경 후 (09-16~17) | 750 | 208 | **27.7%** | [24.6, 31.0] |

일자별로도 계단이 없다: 09-10 31.5% · 09-11 34.7% · 09-15 20.8% · 09-16 28.6% · 09-17 26.4%
(전부 CI 겹침). **단위 변경은 결과를 움직이지 않았다.**

왜 안 무나. 두 체계 모두 **수치적으로 자기충족**이다 — 모델이 v 를 명령하면 조는 v 로 가고
proprio 는 v 를 돌려준다. 모델은 오차를 볼 수 없고, 남는 건 v→물리 개구의 단조 재매개화뿐이다.
그리고 핑거 시트 기하가 그 폭을 흡수한다: v=8 이 5.7 mm 든 8.0 mm 든 둘 다 12 mm 섕크보다
한참 좁아 볼트는 어느 쪽이든 팁 위 시트에 걸린다. 조 위치·모터 전류를 지표로 못 쓰게 만든
바로 그 기하가, 단위 오차도 무해하게 만든다.

→ **09-16 수정이 성능을 떨어뜨렸다는 §1 의 서술을 철회한다.** 그 근거였던
"carry 16%/28% → 1%/10%" 는 이미 철회된 CARRY 프록시에서 나온 수치이고, 배달율로 보면
그런 하락은 없다. §2 의 불일치는 코드 사실로 유효하고 위생상 고칠 값어치는 있지만
(핑거나 볼트가 바뀌면 물린다), **런을 멈추고 고칠 일은 아니다 — 상한이 1.3 포인트, 잡음 안이다.**

## 6. 그러면 실제로 무엇이 무나 (proprio=actual 전체 1,662 시도)

|  | 조 개구 < 20 mm | 20–28 mm | ≥ 28 mm |
|---|---|---|---|
| **깊이 OK** (바닥 z ≤ −0.282) | 41.6% (n=267) | 62.6% (n=246) | **68.9%** (n=122) |
| **얕음** | 6.1% (n=674) | 14.5% (n=331) | 4.5% (n=22) |

1. **깊이가 지배항이다.** 시도의 **38%만** z ≤ −0.282 에 도달한다. 못 가면 6~14%.
2. 깊이가 맞은 안에서 조 개구가 41.6% → 68.9% 를 더한다 (M12 헤드 18~21 mm 보다
   충분히 벌어져 있어야 손가락이 볼트를 쳐내지 않는다).
3. 닫는 타이밍: 바닥 도달 후 **0~0.8 s** 에 닫히면 57%, 그보다 먼저면 7%, 늦으면 12%.
4. `--gripper-proprio-source command` 는 **5.0%** [2.3, 10.6] vs `actual` 27.7% — 5.5배 차이.
   런이 통째로 실패했다면 이것부터 확인할 것.

두 좋은 조건이 동시에 만족되는 시도는 전체의 **7.3%** 뿐이다.

주의: 2·3 은 상관이지 인과가 증명된 건 아니다. "그 시도에서 모델이 확신이 있었다"의 증상일 수
있다. 깊이(1)는 §3 의 단조 곡선이 있어 더 강한 근거를 갖는다.
